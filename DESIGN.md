# ClipPanel: a Win+V-style Clipboard Manager for macOS

Design document, v1.0 (2026-08-18). Written for implementation by a later session; assumes no prior context beyond this repo.

Working name: **ClipPanel** (placeholder, trivially renameable). Host toolchain verified: Xcode 26.6, macOS 26.5.2, macOS SDK 26.5.

---

## 1. Goal

Recreate the Windows 10/11 Clipboard History experience (Win+V) on macOS with feature parity, and make it as secure as the platform allows: zero added attack surface, secrets never captured, retained data encrypted, nothing leaves the machine.

### 1.1 On "100% secure"

No software is 100% secure, and a clipboard manager is by nature a sensitive-data aggregator. What we can honestly commit to is a threat model (section 4) with explicit guarantees and explicit non-guarantees. Notably, macOS 26 (Tahoe) now surfaces system alerts when apps read the pasteboard programmatically, which for the first time gives users OS-level visibility into clipboard snooping; our app works with that system, not around it.

## 2. Feature parity matrix (Windows Clipboard History -> ClipPanel)

| Windows behavior | ClipPanel equivalent | Notes |
|---|---|---|
| Win+V opens popup panel near caret | Global hotkey (default ⌃⌘V) opens non-activating panel near text caret, falls back to mouse pointer | ⇧⌘V is NOT the default: it collides with "Paste and Match Style" in most Mac apps. Hotkey is user-configurable. |
| History holds up to 25 items | 25 items default, configurable 10 to 100 | |
| Per-item cap ~4 MB | 4 MB default cap per item, configurable | Oversized copies are simply not recorded (current-clipboard passthrough unaffected) |
| Text, HTML, bitmap images | Plain text, RTF, HTML, PNG/TIFF images, file URLs | Original pasteboard types preserved for fidelity re-paste |
| Click an item to paste into the active app | Click or Return pastes into the frontmost app via synthetic ⌘V | Requires Accessibility permission; degraded "copy to clipboard only" mode without it |
| Pin items (survive Clear All and reboot) | Pin items; pinned items persist, encrypted at rest | |
| Delete single item; Clear All (keeps pinned) | Same | |
| History cleared on restart/sign-out except pinned | Unpinned history is RAM-only and never written to disk, so this happens by construction | Stronger than Windows: unpinned items cannot be recovered forensically from disk |
| ⋯ menu per item (pin, delete) | Hover/focus actions per item: pin, delete, paste as plain text | |
| Cloud sync across devices | **Out of scope, deliberately** (see 3) | |
| Emoji / GIF / symbols tabs (Win11) | **Out of scope**; macOS has native ⌃⌘Space | |

## 3. Explicitly out of scope (v1)

- **Cloud sync / any networking.** The app contains zero networking code. This is a security feature, not a missing feature.
- Emoji/GIF/kaomoji tabs.
- iCloud/Handoff universal clipboard integration (the OS already does this independently of us).
- Mac App Store distribution (see 6.4; sandbox conflicts with auto-paste). Revisit post-v1.
- Search within history (fast follow candidate, not in Windows parity set anyway).

## 4. Security model

### 4.1 Threat model

Assets: clipboard contents (potentially passwords, tokens, PII, proprietary text/images).

| Threat | In scope? | Mitigation |
|---|---|---|
| Other local malware reading the *system* pasteboard | Platform-level; not ours to solve | macOS 26 pasteboard privacy alerts now cover this OS-wide. We add nothing to this surface. |
| Our persisted data read from disk (theft, backup leak, other user account) | Yes | Unpinned history never touches disk. Pinned items AES-256-GCM encrypted, key in Keychain (ThisDeviceOnly, never synced). |
| Capturing secrets from password managers | Yes | Honor `org.nspasteboard.ConcealedType` (set by 1Password, Keychain Access, Bitwarden etc.): never record. Also honor `org.nspasteboard.TransientType` and `org.nspasteboard.AutoGeneratedType` (skip by default, toggleable). |
| Capturing secrets from apps that do not mark them | Partially | Per-app exclusion list (default-populated with known password managers and terminals opt-in); "pause capture" menu item; optional auto-clear on screen lock. |
| History visible in screen sharing / screenshots | Yes | Panel window `sharingType = .none` so it is excluded from screen capture. |
| Data exfiltration by the app itself / supply chain | Yes | Zero third-party dependencies (no SPM packages at all). Zero networking code. Hardened Runtime, notarized. Auditable: the whole app is a few thousand lines of first-party Swift. |
| Contents leaking into logs / crash reports | Yes | `os_log` with `.private` everywhere near payloads; rule: no payload bytes or previews ever formatted into any log string. |
| Memory scraping of our process | Residual risk, documented | Swift `String`/`Data` cannot be reliably zeroized (copy-on-write). We minimize lifetime (drop payloads on trim/delete) but do not claim memory hardening. |
| Evil maid / unlocked machine | Out of scope | Same exposure as the pasteboard itself; auto-clear-on-lock option reduces the window. |

### 4.2 Guarantees (testable, each maps to a test in section 10)

1. No network connections, ever (verify: no networking symbols linked; runtime check with Little Snitch / `nettop` in test plan).
2. Unpinned history exists only in process memory. No file, no SQLite, no UserDefaults, no swap-adjacent temp files written for unpinned items.
3. Pinned items on disk are AES-256-GCM ciphertext; key lives in the login Keychain with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` and is not in any backup that excludes Keychain.
4. Items marked `ConcealedType` are never recorded, with a unit test against a simulated 1Password copy.
5. Excluded apps' copies are never recorded (matched by bundle ID of the frontmost app at copy time).
6. Payload contents never appear in unified log output.
7. The panel never appears in screen recordings or screenshots.

### 4.3 Non-guarantees (stated honestly in the README/onboarding)

- Cannot stop other processes from reading the system pasteboard (macOS 26 alerts mitigate OS-wide).
- Cannot zeroize Swift-managed memory deterministically.
- Cannot detect secrets that source apps fail to mark as concealed, beyond the exclusion list heuristics.

## 5. Architecture

```
┌────────────────────────────────────────────────────────────┐
│ ClipPanel.app (menu bar agent, LSUIElement, no Dock icon)  │
│                                                            │
│  HotKeyManager          ClipboardMonitor                   │
│  (Carbon                (Timer 200ms, NSPasteboard         │
│   RegisterEventHotKey,   changeCount diff; type filters;   │
│   no permission needed)  exclusion + concealed checks)     │
│        │                        │                          │
│        ▼                        ▼                          │
│  PanelController  ◄────  HistoryStore (actor)              │
│  (NSPanel, non-          - unpinned: in-memory ring        │
│   activating,            - pinned: via PinStore            │
│   SwiftUI content,              │                          │
│   caret positioning)            ▼                          │
│        │                 PinStore + CryptoBox              │
│        ▼                 (AES-256-GCM file, Keychain key)  │
│  PasteInjector                                             │
│  (writes item to NSPasteboard, then CGEvent ⌘V;            │
│   requires Accessibility; falls back to copy-only)         │
└────────────────────────────────────────────────────────────┘
```

Components:

- **AppDelegate / ClipPanelApp**: `MenuBarExtra` (or NSStatusItem) with a small menu: Open panel, Pause capture, Settings, Quit. `LSUIElement = YES`.
- **HotKeyManager**: Carbon `RegisterEventHotKey`. Still fully supported, works without any TCC permission (unlike `NSEvent.addGlobalMonitorForEvents`, which needs Input Monitoring). Configurable via a hotkey recorder in Settings.
- **ClipboardMonitor**: polls `NSPasteboard.general.changeCount` every 200 ms (there is no notification API for pasteboard changes on macOS; polling is what every clipboard manager does; cost is negligible). On change: read types first, run filters (concealed/transient/excluded-app/size), then read data only if recordable. Skips changes that ClipPanel itself made when pasting (tracked via its own changeCount marker).
- **HistoryStore** (Swift `actor`): ring buffer of unpinned `ClipItem`s (cap N), plus pinned list. Dedup: re-copying an existing item moves it to top instead of duplicating (Windows behavior). Emits updates via `AsyncStream` / `@Observable` projection for UI.
- **PinStore + CryptoBox**: persistence for pinned items only. Single encrypted container file in `~/Library/Application Support/ClipPanel/pins.enc`. CryptoKit `AES.GCM`, 256-bit symmetric key generated once and stored as a Keychain generic password (`ThisDeviceOnly`). File format: versioned header + sealed box of a Codable payload (items with their raw pasteboard representations).
- **PanelController**: `NSPanel` with `.nonactivatingPanel` style (critical: the target app must keep key focus so paste lands in it), `level = .floating`, `sharingType = .none`, `collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary]`. Hosts SwiftUI content via `NSHostingView`. Positioning: try the focused UI element's caret bounds via AX (`kAXBoundsForRangeParameterizedAttribute` on the focused element); fall back to `NSEvent.mouseLocation`; clamp to screen.
- **PasteInjector**: writes the chosen item's full type set to `NSPasteboard.general`, then synthesizes ⌘V with `CGEvent(keyboardEventSource:virtualKey: 9, keyDown:)` posted to the session event tap. Requires Accessibility (`AXIsProcessTrusted`). If not granted: falls back to copy-only (panel shows "copied, press ⌘V"), and onboarding/settings offer the permission flow. "Paste as plain text" variant writes only `.string`.
- **Permissions/Onboarding**: first-run window that walks through the two system gates (see 6.1, 6.2) with live status checks.

Concurrency: Swift 6 language mode, strict concurrency. UI on `@MainActor`; `HistoryStore` an actor; monitor timer on main (cheap) handing payloads to the actor.

No third-party dependencies anywhere, including the hotkey recorder (write a minimal one; it is ~100 lines).

## 6. macOS platform constraints (the landmines, and decisions made)

### 6.1 macOS 26 pasteboard privacy alerts (the big one)

Since macOS 26 (Tahoe), programmatic pasteboard reads without a user paste gesture trigger a system alert per app, with the user choosing to allow or deny; the setting lives under System Settings > Privacy & Security. A clipboard manager polls the pasteboard by design, so:

- First-run onboarding must explain the upcoming system prompt and tell the user to choose "Always Allow".
- Use `NSPasteboard.general.accessBehavior` (macOS 15.4+ API) where available to detect the current state and show accurate status in Settings, with a deep link to the right Settings pane.
- Where a types-only peek suffices (e.g. deciding whether to skip a concealed item), prefer reading type identifiers before payload data; keep full reads to exactly one per clipboard change.
- Handle denial gracefully: capture pauses, menu bar icon shows a warning state, panel explains why history is frozen.

### 6.2 Accessibility permission (for auto-paste)

Synthetic ⌘V via `CGEventPost` requires the app to be AX-trusted. `AXIsProcessTrustedWithOptions([kAXTrustedCheckOptionPrompt: true])` triggers the system prompt. Without it the app still works in copy-only mode. Status shown live in onboarding and Settings.

### 6.3 No pasteboard change notifications

Poll `changeCount` at 200 ms. Do not attempt private APIs.

### 6.4 Sandbox vs auto-paste (distribution decision)

App Sandbox blocks posting synthetic HID events to other apps, which kills the core "click to paste" interaction. Decision for v1: **non-sandboxed, Developer ID signed, Hardened Runtime, notarized, direct distribution**. Consequences acknowledged: no MAS; the "no networking" guarantee is by construction and audit rather than entitlement-enforced. A future MAS build could ship with copy-only paste behavior.

### 6.5 Hotkey default

⌃⌘V. Rationale: Win+V maps naturally to a V-chord; ⇧⌘V is taken by "Paste and Match Style"; ⌥⌘V is Finder's "Move Item Here". Configurable regardless.

### 6.7 Non-activating panel: measured focus behaviour (M1 finding)

Measured with an isolated AppKit probe, not assumed:

- `orderFrontRegardless()` alone leaves `NSApp.isActive` false.
- `makeKey()` on a panel with `.nonactivatingPanel` sets `NSApp.isActive` to **true**, while
  `NSWorkspace.frontmostApplication` stays on the other app.

So `NSApp.isActive` is NOT a useful signal for "did we steal the user's focus"; the real signal
is `frontmostApplication`. The panel must take key status (arrow keys, Return), the user's app
stays frontmost and keeps its caret, and this matches what Win+V does on Windows.

**Consequence for M4:** the panel genuinely holds key focus while open, so the paste path cannot
simply post command-V. It must hide the panel, reactivate the recorded app
(`PanelController.appToRestoreFocusTo`), and only then synthesize the keystroke.

### 6.6 Deployment target

macOS 26.0 minimum. Simplifies pasteboard-privacy handling to one behavior generation, and matches the host. (Supporting 14/15 would add conditional paths; not worth it for v1.)

## 7. Data model

```swift
struct ClipItem: Identifiable, Sendable {
    let id: UUID
    let createdAt: Date
    let sourceBundleID: String?       // frontmost app at copy time
    var isPinned: Bool
    let representations: [Rep]         // original pasteboard types, fidelity re-paste
    let preview: Preview               // derived once at capture
    let byteSize: Int

    struct Rep: Sendable { let type: String /* NSPasteboard.PasteboardType raw */; let data: Data }
    enum Preview: Sendable {
        case text(String)              // first ~500 chars, whitespace-collapsed
        case image(thumbnailPNG: Data) // longest side <= 128 px
        case fileURLs([String])        // display paths
    }
}
```

Capture rules, in order:
1. Change originated from ClipPanel's own paste -> skip.
2. Types include `org.nspasteboard.ConcealedType` -> skip, always, not configurable.
3. Types include Transient/AutoGenerated -> skip (default on, toggleable).
4. Frontmost app in exclusion list -> skip.
5. Capture paused -> skip.
6. Total payload > per-item cap -> skip.
7. Content-equal to an existing item -> move existing to top (preserve its pin state).
8. Otherwise record; evict oldest unpinned beyond cap N.

Persistence (pinned only): `pins.enc` = magic + format version + AES-GCM sealed box over `Codable`-encoded `[ClipItem]`. Rewrite atomically on every pin/unpin/delete. Corrupt or undecryptable file: rename aside, start empty, log privately.

## 8. UI spec (mirroring Win+V closely)

**Panel**: ~360 pt wide, max ~480 pt tall, rounded-corner material background (`.hudWindow`-like), appears at caret/pointer.

- Header row: "Clipboard" title, Clear All button (right). Clear All removes all unpinned items (matches Windows).
- Scrollable card list, newest first. Each card:
  - Text: up to 4 lines preview, monospace if content looks like code (heuristic optional, low priority).
  - Image: thumbnail, dimensions caption.
  - Files: icon + names.
  - Affordances on hover/keyboard focus: pin/unpin (pin glyph, filled when pinned), delete (x), overflow for "Paste as plain text".
  - Small caption row: source app name + relative time (Windows omits this; keep it, it is genuinely useful; toggleable if purism wins).
- Pinned items: pinned section stays at top (Windows shows pin state inline; we keep inline but stable-sort pinned first; verify against real Win11 during implementation and match).
- Empty state: mirrors Windows copy: title "Clipboard" / "Nothing here yet. Copy something to see it saved."
- Keyboard: ↑/↓ move, Return paste, ⌥Return paste as plain text, ⌘P toggle pin, Delete remove, Esc close. Panel opens with first item focused so Win+V muscle memory (hotkey, Return) works.
- Click-through protection: panel closes on paste, on Esc, and on click outside (global mouse monitor).

**Menu bar item**: clipboard glyph; menu with Open Clipboard (hotkey shown), Pause Capture (checkmark toggle), Clear All, Settings…, Quit. Warning badge state when pasteboard access is denied.

**Settings window** (standard `Settings` scene, 3 tabs):
- General: hotkey recorder, history size (10..100, default 25), per-item cap (1..32 MB, default 4), launch at login (`SMAppService.mainApp`), show source app captions.
- Privacy: skip transient/auto-generated toggle, excluded apps list (add via app picker; ships with suggested defaults: 1Password, Bitwarden, KeePassXC, Keychain Access), auto-clear on screen lock toggle, capture pause.
- Permissions: live status rows for Pasteboard access and Accessibility with "Open System Settings" buttons; explanation of copy-only degraded mode.

**Onboarding (first run)**: 3 short steps: what it does (with the honesty paragraph from 4.3), pasteboard permission walkthrough, accessibility walkthrough (skippable -> copy-only mode). Never shown again unless permissions regress.

Notable implementation decisions taken during M1:

1. **Hot key actions live in a main-actor table, not a `userData` pointer.** The Carbon callback
   is a C function pointer and Swift 6 refuses to send a non-Sendable object through
   `userData`. Actions are keyed by hot key id in a `@MainActor` global, and the callback looks
   them up inside `MainActor.assumeIsolated` (Carbon delivers on the main run loop).
2. **Dismiss on resign-key rather than a global mouse monitor.** Same behaviour for clicks
   outside the panel, no permission required.
3. **`sharingType = .none` is set at panel creation**, so guarantee 7 holds from M1 rather than
   waiting for M7 to bolt it on.
4. **Carbon name collisions:** `EventModifiers` must be spelled `SwiftUI.EventModifiers`, and
   `ByteCount` is not visible to Swift (use an inferred integer init).

CLIPPANEL_SELFTEST=1 ./ClipPanel.app/Contents/MacOS/ClipPanel   # 13 checks, exits 0

### M2 complete (2026-08-18)

Capture pipeline, history store, live panel list, and a unit test target. 55 test cases passing,
self test extended to 22 checks and still green.

Files added: `Model/PasteboardTypes.swift`, `Model/ClipItem.swift`, `Model/CaptureSettings.swift`
(with `ExclusionList`), `Model/CaptureRules.swift`, `Model/PasteboardSnapshot.swift`,
`Model/ItemFactory.swift`, `Model/HistoryStore.swift`, `Core/PasteboardSource.swift`,
`Core/ClipboardMonitor.swift`, `UI/HistoryRowsView.swift`, `UI/ItemRowView.swift`,
`UI/AppNameResolver.swift`, plus the `ClipPanelTests` target (hand-authored into the pbxproj,
file-system synchronized, app hosted, Swift Testing).

Four decisions that depart from the design as written, each on purpose:

1. **Capture rules are two phase, not one ordered list (was section 7).** `decideBeforeReading`
   judges from type identifiers alone, so a concealed, excluded, paused, or unsupported copy is
   rejected with **zero payload reads**; `decideAfterReading` handles size and usability, which
   genuinely need the bytes. This upgrades the concealed-copy guarantee from "we did not keep
   the password" to "we never read it", and keeps payload reads at one per captured change,
   which is what the macOS 26 privacy alert counts. Two tests assert `payloadReadCount == 0` on
   the concealed and excluded-app paths.
2. **`ClipItem` stores representations per pasteboard item (`[[Representation]]`), not flat
   (was section 7).** A multi-file copy puts several items on the pasteboard and a flat list
   cannot reproduce it. Changed now, before M5 makes the shape permanent in an encrypted file.
3. **`HistoryStore` is an `@Observable` main-actor class, not an actor (was section 5).** It
   holds 25 small entries mutated only from the monitor and the panel, both already on the main
   actor, so an actor would buy async hops and an observation bridge for no contention benefit.
   The expensive work (SHA-256, thumbnailing) sits in `ItemFactory`, which is `nonisolated` and
   can move off the main actor on its own if profiling asks.
4. **The history limit counts unpinned entries only.** Pinning is the user saying "keep this",
   so a pin is never evicted to make room, and pinning something does not silently shrink the
   history.

Also worth knowing:

- **Oversized copies are abandoned mid-read.** `readSnapshot(maxBytes:)` stops and discards as
  soon as the running total passes the cap, so a pathological 500 MB copy is never fully pulled
  into memory just to be measured and thrown away.
- **The pre-launch clipboard is not collected.** The monitor starts level with the current
  change count, so whatever was copied before ClipPanel started is not ours.
- **A copy made while paused stays uncaptured after resuming.** The change counter advances even
  on skipped changes, which a test pins down. Pause means paused, not deferred.
- **Polling runs in `.common` run loop mode**, so capture keeps working while a menu is open or
  a window is being dragged.
- **Denial path is wired before the happy path**, as planned: `NSPasteboard.accessBehavior`
  (confirmed present in the 26.5 SDK, macOS 15.4+) is surfaced as `PasteboardAccess`, the panel
  shows an explanatory state instead of looking empty and broken, and the menu says so too.
- **Tests do not start the live monitor.** `AppDelegate` skips `coordinator.start()` when
  hosting tests, so a test run cannot raise the pasteboard prompt (which would hang the run),
  read the developer's real clipboard, or fight a running copy of the app for the hot key. Test
  fixtures use a `FakePasteboard`, never `NSPasteboard.general`.

**Bug found and fixed during M2, worth remembering:** wrapping the list in a `ScrollView` sized
the whole panel as though it held one row (178 pt empty, 179 pt with 12 entries). A ScrollView is
content with any height, so `NSHostingView.fittingSize` returns near its minimum, and a
`LazyVStack` compounds it by only building the rows that fit. Fix: `PanelController` measures
`HistoryRowsView` in a throwaway hosting view, then passes an explicit `listHeight` in, and the
rows use a plain `VStack`. Same 12 entries now produce 438 pt. The self test had *passed* this
bug because it only asserted "taller than empty", so it now asserts a real threshold. Lesson for
later milestones: assert magnitudes, not directions.

### Image capacity (2026-08-18, after live verification)

Prompted by the direct question "does it include copied images, what about screenshots". A live test
against the shipping build settled it: a pasteboard item carrying a 47 KB PNG plus a 10 MB TIFF was
captured and stored as 48,801 bytes across one representation. Screenshots work, and the P0 slimming
fix is why.

Two limits then replaced the single 4 MB text cap, because "no limit" is not a real answer for
something that holds twenty-five entries in RAM:

- **Per-item cap, chosen by content.** Images are judged against `maxImageItemBytes` (64 MB default,
  clamped 8 to 256), everything else against `maxItemBytes` (4 MB default). The monitor also READS
  against the content-appropriate cap, so a large screenshot is never abandoned mid-read.
- **Total unpinned byte budget**, `maxTotalBytes` (256 MB default, clamped 64 to 4096). Exceeding it
  evicts oldest-unpinned-first, the same order the count limit uses. Pinned entries neither count
  against it nor get evicted by it.

One rule in the eviction loop is load-bearing and easy to get wrong: the budget never evicts the
last remaining unpinned entry. Without that, a screenshot larger than the whole budget would be
captured and then immediately evicted to satisfy the budget, reproducing the exact "screenshots
silently vanish" bug from the other direction. A test pins this down.

### Search (2026-08-19)

Type-to-filter, Maccy-style, because the panel already owns the keyboard: no search field, no focus
battle with the non-activating window. Printable keystrokes build a query shown in a search row under
the header, Backspace edits it (and only deletes the selected entry when the query is empty, keeping
the original binding), Escape backs out one layer at a time: query first, panel second. Selection
jumps to the first match on every keystroke so "type a few letters, Return" pastes the top hit.
Matching is case- and diacritic-insensitive substring with AND-combined tokens, over text previews,
file paths, and the source app's name.

Two decisions worth recording:

1. **Guarded entries never participate in a search, not even by app name.** A masked row that
   appears or disappears as you type is a confirmation oracle: type the password you suspect and the
   filter confirms it character by character without ever unmasking anything. `SearchFilter` drops
   guarded entries from any non-empty query, all or nothing, and the no-matches state says so when
   guarded entries exist. Tests pin the exclusion down, including the app-name path.
2. **The view never filters for itself.** `PanelController.visibleItems` is the single filtered
   list; the keyboard commands, the selection, the size measurement, and the rendered rows all
   consume it, so what the arrows move over and what is drawn cannot disagree.

~~Known limitation, deliberate for now: without a real text view there is no input-method
composition, so dead keys and CJK input do not compose in the search box.~~ Resolved the next day:
the display row was replaced with a real TextField after the obvious complaint arrived ("the search
is not clickable"). The field is clickable, shows a cursor, supports selection and input-method
composition. Keeping the keyboard model intact required two layers: the deterministic one is a
`sendEvent` override in `PanelWindow` that routes the unconditional list keys (arrows, Return,
forward delete, Escape) into the command handler before the field editor sees them, EXCEPT while
marked text exists, because during CJK composition Return confirms the composition and arrows
navigate candidates. Backspace stays with the field, which knows the query state: it edits an
active query and deletes the selected entry otherwise (routed via onKeyPress). The controller's
query handling is guarded by a last-handled check, since field edits and keyboard commands report
the same change through two paths a runloop apart.

Incidental fix: `verify-release.sh`'s hardened-runtime check was flaky under `pipefail`, because
`grep -q` exits on first match and can SIGPIPE `codesign`, failing the pipeline despite the flag

### Login item self-healing (2026-08-30, field failure)

Reported: "Open at login" was toggled on, and after an update plus restart the app did not launch.
Diagnosis from the BTM database (`sfltool dumpbtm`): the record existed, enabled, at the right path,
with Generation 3 and NO team identifier. That last part is the cause. An ad-hoc signature has no
stable identity, so the identity BTM records is effectively the hash of one specific binary; every
reinstall since the toggle had replaced that binary, and at boot BTM validates, fails the match, and
silently launches nothing while the toggle still reads as on. The unified log shows none of this to
an unprivileged query because the relevant entries are redacted.

Fix shipped: on every launch, when the system reports the login item ENABLED, the app re-registers
itself, which rewrites the BTM record with the running binary's identity. Gating on enabled is
deliberate: it is exactly the broken state, and it guarantees a user who disabled ClipPanel directly
in System Settings is never fought. The toggle also records intent in preferences now
(`launchAtLoginDesired`), migrated automatically for toggles that predate it.

Consequence for users on ad-hoc builds: after any update, the first manual launch heals the login
item automatically; launching the app after updating is therefore the whole maintenance procedure.
A Developer ID signature removes the problem at the root, because its identity is stable across
updates. That remains the standing recommendation for the credential-gated release step.

Tooling note for whoever debugs BTM next: unprivileged `sfltool dumpbtm` worked exactly once per
session here, then hung or returned empty. Guard it with a timeout, take its first answer, and do
not build a verification loop on it. The definitive test of a login item is a restart.

### Hover no longer changes layout (2026-10-06, PLAN.md Item 2)

does not repeat on cue. Eight consecutive runs clean afterwards.

### Liquid Glass (2026-10-06, PLAN.md Item 3)

Spike first, as planned, and it changed the plan. The glass APIs exist in the macOS 27 SDK (in
SwiftUICore, available from macOS 26.0, matching the deployment target). The plan's open question
was whether SwiftUI `.glassEffect` on a view inside a borderless transparent NSPanel would sample
what is behind the window. It could not be answered by screenshot: the panel is excluded from screen
capture by design, and capturing the user's desktop to find out was not acceptable. AppKit answers
it differently: `NSGlassEffectView` is the framework's container for embedding a window's content in
glass, with its own corner radius. For an AppKit-owned panel that is the canonical route, so the
panel's content view is now an `NSGlassEffectView` wrapping the SwiftUI hosting view, and the SwiftUI
root dropped its `.regularMaterial` background and hand-drawn stroke (the clip stays, so scrolling
content cannot paint past the corners). The controller now holds the hosting view directly and
measures it, since the glass container has no intrinsic size and the old `contentView as?
NSHostingView` cast would have silently stopped updating the panel. The self test asserts the
content is glass, and sizing, focus, and capture exclusion all still pass.

Deliberate departures from the plan, each with its reason:

- **No glass selection pill.** The panel is glass now, and Apple's guidance is not to layer glass on
  glass. The selection highlight instead slides between rows via `matchedGeometryEffect` in a shared
  namespace, which is the motion the plan wanted.
- **Row actions stay borderless.** A glass capsule on every row of a dense list would be heavy.
  Clear All uses `.glass`, the onboarding primary button `.glassProminent`.
- **No `glassEffectTransition`.** The container is AppKit's, so the panel keeps its window-level
  `.utilityWindow` entrance animation; choosing one, as the plan said, means this one.
- **Icon Composer icon deferred.** `.icon` files are authored in Apple's Icon Composer app; writing
  that format by hand would be guesswork. The PNG set keeps working inside Tahoe's legacy wrapper
  until someone builds the layered icon in the app.

Needs a human eye, and is on the review checklist: how the glass actually reads over a busy desktop,
light and dark, and with Reduce Transparency on. None of that is visible to a headless run.

### README repositioned (2026-10-06, PLAN.md Item 4)

New section "Versus the clipboard history in Spotlight". It states the one fact about Spotlight's
built-in history that this project is confident of (about eight hours of recent copies, built in,
since macOS 26) and says plainly that if that covers you, you do not need ClipPanel. Everything
else is framed as what ClipPanel adds, rather than as claims about what Spotlight lacks, because
those details change between releases and a README that misdescribes a competitor is worse than one
that does not describe it. Secret Guard is listed as optional. The usage section now covers the
menu bar's recent entries and their screenshot limitation.

### On-device model spike: negative, not integrated (2026-10-06, PLAN.md Item 6)

Question: could Apple's on-device Foundation Models help the secret detector with the cases
heuristics handle worst (secrets made of words, random-looking text that is not secret)? Measured on
this Mac (Apple M5 Pro, macOS 27, model available) with a standalone script and eight synthetic
inputs, one fresh session per input, a one-word yes/no instruction:

- Accuracy 4 of 8. It said no to `correcthorsebatterystaple`, `Summer2024!`, and `hunter2`, and yes
  to a git short hash. That is a coin flip on exactly the cases it was meant to help with.
- Latency: median 250 ms, first call 2,028 ms. The plan's disqualification line for the capture
  path was 50 ms.

Verdict: not integrated, not even behind a flag. Moving it to a background pass would fix latency
but not accuracy, and with Secret Guard now off by default the payoff is smaller still. Worth
re-running only if a future model or a structured-output prompt changes the accuracy picture; the
script was throwaway, but the eight inputs above are the benchmark to beat.
